# VALIDATIONS — single-node model test against a representative pattern set

Validation of the single-node model (`docs/ARCHITECTURE.md`) using a
**fictitious in-repo domain** only. No consumer patterns, names or data live in
this repository (see AGENTS.md rule 7). The pattern shapes exercised here are
representative of composite patterns in general, expressed in the **unified
composite model** (LEG-044: `type: composite` + `branches`; steps are bare
pattern names; one composite runner for every arity).

## Setup

One node serving a full roster locally: several `main` patterns (starting
agents) + one tool + several linguistic atomics + composites (single-branch
and multi-branch). Each agent = one queue + one pool; one beaver; API +
Runtime.

## Traces

### `main_a` (smallest main)

`[tool_extract → composite [summ, cata, keys]]`

1. **API** `submit(main_a, {payload})` → `task_id T`, inputs staged, root token
   `[main_a]`, `root=True`, `root branch_id` (autogenerated, never empty —
   ARCHITECTURE §3),    `end_of_level_queue = result_queue_key(main_a)` →
   queue `main_a`.
2. **main_a** (single-branch composite, index 0) deposits to `tool_extract`
   (tool). Result `{text, lang}` re-keys to main_a...
3. index 1 → composite → deposit to `main_a_processors` (its inbox + gathering
   queue) with the branch routes `[summ]`, `[cata]`, `[keys]`.
4. Fan-out to the 3 class queues with a fresh `branch_id` per branch; each
   child returns an `ExecutionResultMessage` to `main_a_processors`' gathering
   queue; **fan-in dedupe per (composite, task, branch_id)**, bookkeeping
   `state:composite:<class>`.
5. **Payload built from branch results** `{summ, cata, keys}` constructed under
   main_a's `output_as` (construction + re-keying, no accumulation) → final
   index → delivery to the final-result queue.

### `main_b` (heavier main, nested composite)

`[tool_extract → composite [summ, cata, keys, goal, draft_flow]]`

1. Same until the composite fan-out, which includes `draft_flow` (a **composite
   as a step**, reused by reference — recursion: it fans out its own
   `[outline_step, draft]` at a deeper level).
2. `draft_flow`: step 0 `outline_step` with `output_as: stage_b`;
   step 1 `draft` reads the value re-keyed under its own `input_as`
   (`{draft...}` produced by `outline_step`).
3. Everything converges: `draft_flow` joins and builds `{draft}` under its own
   `output_as` → its parent composite gathers it alongside the other branch
   results → main_b constructs the final payload → final result.

### Result without structural changes

The model (per-class inboxes, composite gathering queue, payload-in-message
state, pools over shared atomics, delegation) validates this representative
set on one node.

## Design facts the validation rests on

- **Steps are references, never inline definitions.** Each step in a branch is a
  bare pattern name referring to a defined agent; there is no unnamed stage, no
  embedded prompt definition (AGENT_LIFECYCLE §4.12).
- **Explicit read aliases.** A step reads the value re-keyed under its own
  declared `input_as`; a tool's `parameters` are explicit `{input_as}.{key}`
  paths (`§4.12`), never resolved implicitly.
- **Explicit parameters + system vars.** Prompts fill via the re-keyed input and
  system variables (e.g. `current_date`).
- **Construction, not accumulation.** A composite combines its children's
  results and **builds** the next payload via `build_payload` (`{output_as:
  output}`); each step constructs its output under its `output_as`; nothing is
  merged into a growing container.
- **Fan-in by branch_id.** Dedupe per (composite, task, `branch_id`) — not by
  agent name; the composite joins when every slot of the task is filled.
- **Schema compilation.** `output_schema` (unions, arrays, nested objects,
  recursion) compiles to pydantic and is validated at the boundary
  (AGENT_LIFECYCLE §4.12).

## What the traces confirm

- **Two `B`s = two tasks**: every occurrence of a shared pattern is a distinct
  `task_id` + DAG path; the per-task payload (rode through the request/result
  messages) prevents cross-talk between concurrent runs of the shared atomics.
- **Gathering-queue fan-in works** for single-branch and multi-branch composites
  when the dedupe key is per (composite, task, `branch_id`) — not the agent
  name.
- **Pools over shared queues**: the tool and the shared atomics are natural
  pool points on a single node.
- **Root token semantics** (final derived from position + `level`, delivery to
  the task's final-result queue) hold for all `main` patterns.

## Status

Model validated on a single node against a representative (fictitious, in-repo)
pattern set. These design facts are the current acceptance semantics for the
composite engine (LEG-044) and the `{input_as}.{key}` parameter vocabulary.
