# 2026-09-07 — Session 78 — What a legio "contract" is and who reviews it; the coupling misgiving (analysis; no code)

## Scope

The maintainer asked who reviews the contracts and confessed unease: the word "contract" sounds like a bilateral agreement between two components, i.e. coupling. Clarified the meaning of `docs/CONTRACTS/` in legio. No code changed.

## The clarification (as given)

1. **A legio "contract" is a per-issue specification, not an inter-module agreement** — from contract-first TDD: before coding, write the "what it must do" and the tests that pin it. There are no "two parties"; there is ONE deliverable specified against its validation. The name is borrowed; the thing is "spec por issue".
2. **Who reviews it: the maintainer.** Contracts are written as DRAFT; per the process only the maintainer approves an issue (and only the maintainer closes it). Nothing under `docs/CONTRACTS/` is in force until approved.
3. **Contracts are ANTI-coupling, not coupling.** A contract pins the PUBLIC SURFACE of a single module (e.g. the Manager's API `submit_task`/`status`/`control_mode`/…). Consumers must reach through that documented surface, never into internals. Evidence: finding 2 — the Runtime reaching past the surface into the `control` scope *was* coupling, and the contract's "delegate via API" rule is what caught it. The contract draws the boundary; coupling is deleting it.
4. Recap of the catalog-slice status: contracts LEG-083/084/085/086 are DRAFT, awaiting maintainer approval; issues are provisional (#47-#50), held by the maintainer.

## Decisions taken

- **Business submit IS the Manager's `seed` task** — record lives in Manager `tasks` (created via `submit_task` with extra-official kwargs `client_id`/`token`/`payload`); the Manager stays blind (rule 7). No `business_tasks` scope.
- **One-shot bring-up** — `_bring_up_impl` returns `instance_id` immediately (terminal SUCCESS); no parked generator, no instance gate, no `_bring_up_gates`. A boot overwrites this callable at the same seam.
- **Bounded clock waits use lifecycle config** — `_await_observable_state` / `_confirm_control` poll `manager.status` / `control_mode` every `drain_interval` up to `drain_timeout` (resolved per class via `LifecycleConfig.resolve`); FAILED record that predicate rejects raises immediately (rule 9); budget expiry raises visible `RecoverableError` with last state. No `_CONFIRM_PASSES`, no `drain_interval_ms`.
- **Node owns executor** — Runtime exposes `manager` attribute; the node (and tests) drives `manager.run()`. Runtime has no `run()`/`register()`.
- **`destroy_instance` confirms terminal** — the one-shot bring-up is already SUCCESS; a cancel reaching a completed record is a terminal no-op; a pending cancel lands `failed(cancelled)`. Either is the confirmed fact.
- **`drain`/`now` destroy** — `drain` closes gate, waits queue empty (bounded by lifecycle budgets); on timeout → visible error, gate restored. `now` proceeds immediately.
- **Legacy `legio.manager.submit/status` and `api.py` untouched** — pinned `"local:"` behavior preserved; unified when `api.py` re-targets to Runtime (LEG-080/081).
- **`recreate_class` reads cached YAML** — precondition: class does not exist; cache miss → visible `RecoverableError`.
