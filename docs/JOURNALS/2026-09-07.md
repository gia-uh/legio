## Design decisions

- **Naming collision resolved**: `legio.runtime.Runtime` is the orchestrating
  public face (§0/§6); `materializer.NodeRuntime` remains the booted-node bag
  (config/agents/catalog/db/app). Step 4 wires them; the Runtime slice leaves the
  materializer untouched.
- **Park-first bring-up**: yielding after the gate is released is the race-free
  choice (an already-set gate under yield-then-await would drive the generator to
  StopAsyncIteration → stray SUCCESS; park-first re-runs the control check).
- **`_drive_until` (one pass per read, bounded) instead of a single pass**: the
  cancel-on-parked re-enqueue leaves stale pending tickets; a single spawned
  pass could pop a stale ticket (terminal no-op) and never dispatch the new
  bring-up — which the recreate flow proved. Stale tickets for live tasks are
  avoided by never spawning passes during enable/disable and by destroy's
  single-driver rule; the residual multi-process concern is documented as the
  boot executor's (step 4).
- `destroy_class` must compute dependents **before** `remove_class`
  (`class_dependents` returns `[]` for an unknown class — the cascade was
  silently skipped otherwise; surfaced by a test, fixed).
- Born state of instances follows the class's effective state (§4.4/§5.1):
  disabled class ⇒ disabled instances, enabled class ⇒ enabled instances.
- Born-disabled instances still run their parked bring-up vehicle with control
  `run` (registry records `disabled`); setting control `pause` at birth would
  dead-lock the bring-up driver (the pause-on-pending dispatch gate parks the
  task before the callable starts). Recorded as a known deviation for step 4,
  when instances materialize real agents.
- Gates absence = open (a class without a gate row admits submits); rows are
  written only by Runtime lifecycle ops.
- `recreate_class` of a composite whose referenced patterns are absent surfaces
  the loader's `UnrecoverableError` at the standalone re-parse (documented
  limitation in the contract; recreate tests use atomic classes).

# 2026-09-07 — Session 72 — Walkthrough of audit finding 1: the `tasks` dual-schema collision (analysis only)

## Scope

The maintainer asked to walk through the audit findings one at a time, starting
with finding 1 (the `tasks` dual-schema collision), noting that "by definition"
there should not be one. This turn explains, verifies the evidence in source,
and lays out reconciliation options. No code changed.

## Analysis (evidence)

- **Two schemas on `db.dict("tasks")`:** (a) `TaskRecord` — generic, domain-free
  executor record `{task_id, name, args, kwargs, status, enqueued_at,
  started_at, finished_at, result, error}` (AGENT_LIFECYCLE:1038; manager:84-101;
  written by `Manager.submit_task`/`run` at manager:170,241-338; read by
  `Manager.status` manager:177,220). (b) Business flow entry
  `{owner, state, token, payload}` (token = Schema 2 FlowToken) — written by
  `Runtime.submit` (runtime:235-243) and by the legacy `legio.manager.submit`
  (manager:473-481); read by `Runtime.status` and legacy `status`
  (manager:511-533).
- **Why the docs prescribe it:** LEG-085:158 stages the business entry "under
  `tasks`"; AGENT_LIFECYCLE:1038 declares `tasks` = `TaskRecord`. Both contracts
  re-used the historical scope name `tasks` (the business task dict from
  LEG-014/024/025) for the generic Manager's record dict, without reconciling.
- **Latent, not active:** both id-spaces are `<node_id>:<uuid>` with no
  structural discriminator (there is no `kind`/`type` field); separation holds
  *by use* — `Manager` only drives ids it queued in `pending_tasks` (never
  wholesale-iterates `tasks`), `Runtime` only reads ids it minted.
- **Failure modes:** a stray `Manager.status()` on a business id →
  `TaskRecord.model_validate` fails `ValidationError` (missing `name`/
  `enqueued_at`); a stray `Runtime.status()`/legacy `status` on a `TaskRecord`
  → `KeyError` on `data["owner"]`. Latent coupling-by-name violating the §2
  one-scope-one-owner-one-schema discipline.

## Decision options presented to the maintainer

- **A. Separate business scope** — the Runtime's flow records live under their
  own scope name; `tasks` stays = `TaskRecord`. Strict §2; costs renaming the
  historical scope (legacy `submit`/`status` + `api.py` read it today).
- **B. Discriminator field** (`kind: executor|flow`) — additive, keeps the
  scope name; both readers validate their `kind` and reject the other LOUDLY
  (rule 9). Recommended now.
- **C. Document only** — leave as known latent risk.
- Reccommended path: B now; migrate to A when the boot re-targets `api.py`
  (planned in R-8) and the legacy submit/status disappear.

# 2026-09-07 — Session 73 — Audit finding 1 CORRECTED: no `tasks` schema collision (analysis only)

## Scope

The maintainer challenged finding 1: "the TaskRecord the manager puts is the
same as the flow — same ID — the manager is the one that creates the submit".
Verification in source confirms the maintainer is right and the audit
overstated the finding. No code changed.

## Correction (evidence)

- **Business path has ONE schema per ID.** Legacy `legio.manager.submit`
  (manager:472-481) and the re-homed `Runtime.submit` (runtime:235-243) write
  the exact same shape `{owner, state, token, payload}` under `tasks`, keyed by
  the business id minted once by the producer. The manager (legacy) creates the
  submit; the Runtime re-homes the identical contract (LEG-085:158). There is
  no business "TaskRecord" distinct from the flow record — they are the same
  thing. The audit's failure-mode framing (`Manager.status()` on a business id
  → `ValidationError`) implied a reader crossing families, which never happens.
- **The generic `TaskRecord` (`Manager.submit_task`, manager:159-173) is used
  only for Runtime housekeeping** — instance bring-up (`BRING_UP_TASK`,
  runtime:120), resume/cancel — with ids minted separately, never the business
  id. The machinery cannot cross them: `Manager.run()` dispatches only ids the
  Manager queued in `pending_tasks` (the business submit deposits into the
  agent's own queue, runtime:254, never into `pending_tasks`); `Runtime.status`
  reads only ids it minted; the flow routes by `queue_key`/`result_queue_key`,
  not via the `tasks` dict.
- **Conclusion:** no same-ID dual schema exists; each record has a single
  producer keying its own id and a single consumer of that id. "By definition
  there is no collision" — correct.

## Residue (downgraded)

The real (mild) issue is **documentation hygiene**: AGENT_LIFECYCLE:1038
declares `tasks = task_id → TaskRecord` without noting that the scope also
hosts the Runtime's business flow records (`{owner,state,token,payload}`, per
LEG-085:158 and the legacy submit). Suggested fix: a one-line doc amendment
defining the two families and their disjoint-by-minted-id ownership, plus
(optional) a footprint-pinning test. No code change.
