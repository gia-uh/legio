**Decision A — entry gate / "dispatch" belongs to the Runtime (open decision 3,

wording.

**Decision B — lease reaper goes in the minimal TM (open decision 4,
RESOLVED).** Analysis: `get()` destructive atomicity already guarantees

rule 9 (errors never silent). R-6 (LEG-060/061/062) is work *recovery*
(re-queue by `attempts`, DLQ), a different concern from *truth of existence*.
Minimal scope confirmed: lease + `reap()` → `failed(worker_died)`; retry/DLQ at
R-6. §10 open decision 4 marked resolved (behavior already in §6.1, no other
doc change needed).

### Rectified model (now normative, recorded 2026-08-30)

1. **Blackboard travels in the message.** The accumulated state is carried by
   `ExecutionRequestMessage`/`ExecutionResultMessage` themselves; there is **no**
   accumulator board. If anything earlier was staged under "frames
   ({agent}:{task_id})", that is the erroneous "board" idea and it is retracted.
2. **One inbox queue per class** (`legio:queue:<class>`); replicas are
   interchangeable stateless workers of the class unit. No per-leg queue, no
   god agent, no centralized engine.
3. **Parallel = inbox + a gathering queue.** The second queue is part of the
   *model* (conceptual); collapsing it into one physical queue by dispatching
   on message type is an *implementation* choice. **Sequence has no gathering
   queue** — forward-only, nothing returns; the last processor deposits into
   the next class's queue.
4. **`_advance_flow` (single mechanism).** Next step → request into route[
   next_index]'s queue; route end + `ultimate_return_agent_id` → result to the
   returning agent; route end without a return → **the last agent itself saves
   the final result**.
5. **Fan-in bookkeeping per class.** `state:parallel:<class>` (or equivalent),
   locked, keyed by task, deduped by `source_agent_id`, then deleted on
   completion → advance the parent token. Failure → `ExecutionResultMessage`
   with error → unsticks the parallel; never silent (rule 9).
6. **"Where am I / whom do I give the result to?" is answered by the token**
   (`current_index`, `route_pattern_names`, `ultimate_return_agent_id`) and the
   message that carries it — not by any board or engine. This is the CPS
   continuation already implemented in `base.py::_advance`.

   failure** through the existing failure mechanism (result with error), never
   a silent drop.

## Session 12 addendum F — maintainer correction: pool-in-loop removed, slice model (turn 32)

**Maintainer ruling (fury, justified).** (a) `pool_size` in the agent loop is a
design disaster; (b) agents are not workers and tasks are not agents — a

## Session 12 addendum J — pattern schema S1 design thread: tree of types + review (turn 36+)

**Trigger.** Set of maintainer corrections driving the definition of the pattern
(schema) language so it covers the reference (`voice-notes-api`) generically
without mixing the distinct schemas (pattern / resource contract / config /
messages / output sub-grammar). Maintenance of the design required, per the
pautas, that legio never declares a resource's contract inside the pattern and
that every declaration be explicit (nothing inferred by key presence, so the
schema rejects cross-branch fields outright).

**Decisions taken this thread (maintainer-ruled, recorded now).**
1. **Separate schemas, never mixed:** pattern (S1) declares only; each resource
   (S2) defines its contract in code; config/registry (S3) translates a name →
   implementation + policy; the message envelope (S4) carries carried state;
   `output_schema` (S5) is the mini-grammar for shapes inside S1. Materialization
   products (route_names, compiled model, queue names, derived identities) are
   halo artifacts, not schema.
2. **Agent tree by type:** `type` stays and is the root discriminator, with only
   two values: `atomic` | `composite` (reference `main_patterns.yaml:19` abuses
   `type: parallel` — legio does not repeat it). A second explicit discriminator
   `kind` is required and cross-validated: `type: atomic` → `kind` ∈
   {tool, linguistic}; `type: composite` → `kind` ∈ {sequence, parallel}. Class
   of agent = the (type, kind) pair, no inference.
3. **Branch-exclusive fields, structurally enforced:** a tool branch cannot
   carry `prompt`; a linguistic branch cannot carry `tool`; each branch only has
   its own fields. The schema (discriminated union) rejects extraneous fields.
4. **Atomic kinds are exclusive** (a step is either a tool or a prompt — never
   both). **Composites are recursive:** `sequence`/`parallel` children are full
   nodes (atomics or composites); the reference proves it
   (`main_patterns.yaml:19` inline composite in a sequence;
   `text_composite_patterns.yaml:31` inline atomic prompt step).
5. **Every atomic declares its input contract** — `input_type` ∈ {text, json};
   `input_schema` allowed only when json (a `text` input has no fields, so no
   schema). Semantics: the schema says "this node consumes/produces these
   fields", never "only these" — the rest of the carried state passes through
   (matches the reference's flat merge + `{input.*}` + `output_as` namespaces).
6. **Linguistic input contract at the schema level; tool input only as a
   projection** `inputs: {arg: dotted.path}` — the tool's own schemas stay in S2,
   never re-declared in S1 (rule 7 / "do not mix schemes"). (Review finding,
   see below: my earlier tree put `input_schema` on tools too — a mix, corrected.)
7. Out of S1 (mechanism / S3): `max_retries`, `retry_delay_s`, `pool_size`,
   `tool_config`. Materialization artifacts (queue names, derived identity) are
   not schema.

## Session 12 addendum L — tool is executed code, and the ToolAgent handshake (turn 39+)

**Trigger / maintainer corrections (three in a row, all about the tool branch of
the S1 proposal).**

1. "estás tratando a tool como un caso linguistico, no como un codigo que se
   ejecutará y necesita sus parámetros de ejecución" — my `inputs: {alias:
   dotted.path}` treated the tool as a *read projection* like the linguistic
   template aliases. Wrong: a tool is **code that is executed**; its parameters
   are the **execution parameters of the called code**.
2. "no has analizado eso" (how the ToolAgent is invoked in a real flow, what
   appears in its queue, what elements it has, what it looks for) — I had been
   designing the schema in the abstract without grounding it in the runtime:
   the message that arrives, the carried state, the registry lookup, building
   the kwargs, depositing, advancing.

**Corrections absorbed:**
- **Tool ≠ linguistic.** The linguistic fills *template aliases in a text*
  prompt and the LLM answers; there is no external signature to bind to. The
  tool **executes code** (`tool(**kwargs)`); its parameter names, types,
  required/optional and defaults come from the **code's signature (S2)**.
- **The tool branch declares the CALL, not a projection.** Each parameter of
  the executed code is bound to a value source via a discriminated union:
  `{from: dotted.path}` (read from the carried state at runtime), `{value:
  literal}` (a constant of this call), `{default: true}` / omitted (use the
  code's own default). The reviewed runtime flow (`src/legio/agents/tool_agent.py`,
  `src/legio/agents/base.py`, `src/legio/flow/messages.py`, `src/legio/tools.py`):
  1. The ToolAgent's queue receives an `ExecutionRequestMessage`
     (`schema_version`, `route_pattern_names`, `current_index`,
     `ultimate_return_agent_id`, `origin_node_id`, `task_id`, `payload: {input:
     <carried state>}`) plus the `next_run_at` scheduling field (rule 8).
  2. The agent **holds its step spec** from construction (tool name, the
     `parameters` binding, the output projection) — the message carries no
     configuration, only carried state + token.
  3. It resolves the tool by name in the injected `ToolRegistry` (LEG-013/S3),
     reads `payload["input"]`, and for each bound parameter resolves its source
     against the carried state → builds `kwargs` with the **exact parameter
     names of the code**.
  4. Execution: `result = tool(**kwargs)`; result validated against the tool's
     `output_schema` (S2); projected per `output_type`/`output_as`; merged into
     the carried state (`merge_carried`); the token advances
     (`route_pattern_names[current_index + 1]`) or the result is finished.
- **This exposes the current ToolAgent defect (migration target):** today it
  validates the *whole accumulated state* against `input_schema` and passes the
  entire dict as kwargs (`tool_agent.py:57-60`). For a code signature like
  `execute(source, limit=10)` that is a `TypeError: unexpected keyword
  argument` for every foreign carried key. The `parameters` binding is the
  runtime handshake that turns the message's carried state into the exact call.
- **Asymmetry between tool and linguistic is intentional** (correction 2 of the
  forced symmetry of addendum K): the tool binds to the code's signature; the
  linguistic binds to the prompt's text. Output/deposit side stays symmetric.

**Validation errors gained (all detectable):** unknown parameter name vs the
firm's signature; missing required parameter without `{default}`; literal type
mismatch at load; runtime-unresolvable `{from: path}` (visible error result,
rule 9); complete branch rules.

## Session 12 addendum M — `main` as root capability, tool as chain node (turn 40+)

**Trigger / maintainer corrections (this turn).** While refining S1 the
maintainer corrected the framing of the tool and of `main`:

1. I kept *putting the tool at the start* in every example, so its input looked
   like the initial request. Wrong: the tool is **a node of the chain like any
   other** — it can sit mid-chain, and then its input is **the accumulated
   carried state delivered to its queue** (the deposits of previous agents),
   not the initial request.
2. "incluso puede haber dos tool uno tras otro, que la salida de uno (no
   completa necesariamente, sino parte de ella) es la entrada de otro" — two
   tools back-to-back: the output of the first (possibly only **part** of it,
   via its `output_as` namespace) feeds the second's parameters.
3. About `main`: a `main` agent can be the start of a DAG, but it can **also
   appear in the middle of a DAG** — being `main` only grants the root
   capability (return final actions to the client); its functionality can be
   embedded as part of any flow.

**Corrections absorbed:**
- **Tool input is positional, not entry-bound.** The ToolAgent receives the
  carried state in the queue message regardless of where the tool sits in the
  chain (start → reads early deposits/`input.*`; middle → reads prior agents'
  deposits). `{from: dotted.path}` resolves against *the carried state at the
  tool's position*; the pattern never assumes a starting position.
- **Chained tools:** tool1 deposits via `output_as: fetched` (whole output
  namespaced). Tool2 reads only the projected part:
  `parameters: {body: {from: fetched.body}, encoding: {value: "utf-8"}}`. The
  tools never couple: each knows only the carried state and its own signature
  (S2). `parameters` is a **selection**: unbound parameters fall back to the
  code's defaults; required-parameter-unbound is a load error; `parameters` may
  be empty/omitted (call with all defaults).
- **`main` = root capability, not position.** `main: true` marks a pattern as a
  valid `submit` entry (token root, `ultimate_return_agent_id =
  client:{task_id}`). A `main` pattern can also be referenced from the middle
  of another DAG (`pattern: name`): there it executes its functionality as part
  of the enclosing flow and advances (`_advance`), returning to the client only
  when the flow started at it. A catalog may declare several `main` entries.

**Open points.** Await maintainer confirmation that the tool framing is now
correct (position-agnostic chained tools; `{from}` against carried state; root
capability of `main` re-embedable mid-DAG) before writing S1 into
`AGENT_LIFECYCLE.md` (§4.7/§4.10) and rewriting

## Session 12 addendum N — position-invariance: ONE resolution mechanism (turn 42)

**Trigger / maintainer correction.** After showing a "three positions" table
(start = reads client payload, middle = reads prior deposits), the maintainer
caught me introducing **two different ways** of reading parameters depending on
position: "miras los parámetros de un modo cuando inicia, y de otro cuando está
en el medio, no estás analizando nada."

**Correction absorbed — the uniform behavior.** There is exactly ONE ToolAgent
behavior, with no branches on position:
- receive the queued message → `state = payload["input"]` (the carried state,
  whatever it holds);
- for each declared parameter: `{from: path}` → resolve path against `state`;
  `{value: x}` → literal; omitted → the code's default (S2);
- build `kwargs` with the code's exact parameter names; `result = tool(**kwargs)`;
  validate against S2 `output_schema`; deposit per `output_type`/`output_as`;
  `merge_carried` → advance or finish.

`{from: path}` is a single operation against the carried state. Whether that
state is the client's initial payload (start) or includes prior deposits
(middle) is a property of the *data*, never of the agent's position. The agent
never consults its position and never distinguishes the origin of a value;
parameter resolution is a pure function of `(message, parameters, code
signature)`. `main: true` does not touch `parameters` — it only makes the token
born as root (`ultimate_return_agent_id = client:{task_id}`) so a final output
returns to the client. The schema therefore declares only `tool:` + `parameters:`
and no positional role.
