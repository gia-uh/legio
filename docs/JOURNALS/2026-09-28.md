## Work done (analysis)

Read the reference consumer `~/Workspace/voice-notes-api` in full — config,
patterns, `pattern_loader.py`, `agents.py`, `agent_factory.py`,
`workflow_engine.py`, `tasks.py`, `tools.py`, `main.py`, `processing_routes.py`,
`admin_routes.py`, `auth.py`, `models.py`, `cli.py`, `submit_daemon.py` — plus

that a consumer touches: `docs/ARCHITECTURE.md`, `docs/CONSUMER_GUIDE.md`,
`docs/PLAN.md`, `examples/*` (all five nodes), and the materializer / agents /
loader code paths (`boot_node`, `materialize_agents`, `CompositeAgent`,
`LinguisticAgent`, `ToolAgent`, `flow/payload.py`, `patterns/sequences.py`).

Findings (recorded here; no artifacts added to legio — AGENTS.md rule 7 forbids
consumer domain content):

1. **What voice-notes is.** A monolithic FastAPI app with a bespoke engine over
   `beaver-db` + `argo-ai` + `castor-io`. Domain: upload a voice note → external
   STT transcription → a set of LLM text processors (summary, categories, key
   ideas, main goal, events, email draft, to-dos, entities, agenda,
   interventions, agreements, Q&A, article outline, context, conclusion,
   project plan) → structured JSON. 10 "main" patterns (`idea`, `blog_post_draft`,
   `reminder`, `email_simple_draft`, `to_do`, `meeting`, `interview`, `generic`,
   `project_roadmap`) are each `sequence: transcription → parallel: processors`.
   2 composite text processors (`draft_writing`, `executive_summary_flow`).
2. **The legacy engine details that legio already superseded**: a
   `FlowControlToken` carrying a mutable `blackboard`; `SequenceAgent` /
   `ParallelAgent` with per-class `state:parallel:<agent>` dicts + beaver locks
   for fan-out/fan-in; agent-level re-queue retries; a distributed LLM
   semaphore; `PatternLoader` compiling pydantic models from `output_schema`,
   promoting inline composites, and computing reachability; `castor` Manager
   tasks (`run_agent_crew_worker`, `start_voice_note_workflow`); `argo` LLM.
3. **Mapping already provided by legio**: token/messages, standing atomic
   tool/linguistic agents, the unified `CompositeAgent` (branches + gathering
   queue + per-`branch_id` slots, no per-class locks), Runtime/Registry/Manager
   lifecycle with pools, `lingo` structured LLM, Schema 1/3 load+compile,
   client tokens, federation, and the polling host.
4. **Gaps / semantic changes that make the legio version "different"**:
   - **Composite classes are injected programmatically only.** The CLI
     `legio server` calls `boot_node(loaded)` with no `composite_classes` and no
     node-local composite loader, so **any node with a composite cannot boot via
     the CLI**; the five examples' composites are exercised only by tests that
     define and inject a `GatherComposite`. A consumer with composites must
     embed legio in Python (or a new domain-free loader must be added).
   - **Payload is construction + re-keying, not blackboard accumulation.** Each
     step builds exactly `{output_as: value}` and the next reads under its
     `input_as`; the legacy "every processor sees the whole blackboard" (and the
     `find_and_promote_context` hack) do not exist. Parallel processors receive
     the transcription via the composite's re-keying; cross-step context must be
     carried explicitly or by nesting.
   - **No engine retries / no re-queue.** `policy.retries` must be `0` (a
     non-zero value refuses the tool); the legacy `max_retries` / `retry_delay_s`
     and tenacity HTTP retry must move inside the tool implementation.
   - **No distributed semaphore** (docs: future scope) — scale is pool size and
     federation.
   - **Application layer stays in the consumer**: audio upload/storage, user
     auth/quota, the admin token CRUD (stubbed in the legacy app), and the
     Streamlit client. legio owns only submit/status + client tokens + node
     security.
   - **Result shape**: the legacy flattens the blackboard, strips internal keys
     and honors `final_output_key`; legio returns the composite's
     `build_output_as` payload — the new output contract must be declared
     explicitly.
   - **No inline composites / no implicit composition**: every step is a named
     pattern with the mandatory symmetric `input`/`output` triples; the legacy
     main/audio/text hierarchy becomes `patterns/{tool,linguistic,composite}`
     with `main: true`.

# 2026-09-28 — Session 130 (turn 2): legio as a library; consumer design

## Scope

Maintainer answered the three decision questions:
1. **Use legio as a library** ("para que lleve los agentes y los flows") — embed
   the engine in the consumer application, not as a CLI-only node.
2. The new consumer is a **new repository** named **`invoice`**.
3. **Design only** — no plan-by-issues, no code yet.

This turn: record the decisions, verify the exact legio embedding surface, and
produce the consumer design.

## Work done (design)

- Verified the legio library surface an embedder uses: `load` /
  `resolve_config_paths` (`legio.config`), `boot_node(loaded, *,
  lingo_factory=, composite_classes=, ...)` returning `BootedNode`
  (`config`, `agents`, `catalog`, `db`, `runtime`, `client_store`, `agents_db`,
  `app`, `starting_agents`), `Runtime.submit(client_id, route, payload)` /
  `Runtime.status(task_id, client_id)`, and the host helpers exported from
  `legio.cli` (`executor_pump_count`, `executor_loop`, `bring_catalog_up`).
- **Confirmed the embedding friction**: `serve_node` (and the CLI `server`
  command) call `boot_node(loaded)` with **no `composite_classes`**, so the
  ready-made server cannot boot a composite-bearing node. An embedder must
  replicate the small host shell (`boot_node` with classes → `bring_catalog_up`
  → N × `executor_loop` pumps → uvicorn) and can mount/extend `booted.app` or
  drive `booted.runtime` from its own FastAPI app. The host helpers are exported
  but not documented in the consumer guide.
- Produced the consumer design (chat, not yet persisted): boundary (legio =
  engine library; app = voice-note domain), package layout, embedding sequence,
  the composite-class set (one per composite pattern, injected as a mapping), the
  pattern migration (1 tool + 16 linguistic atomics + 11 composites), the
  app-owned layers (upload/storage, user auth, client), and the testing strategy
  (fake STT tool + `MockLLM`, contract tests over the shipped patterns and a main
  flow end-to-end).

## Logging added (rule 11)

- None: design turn, no runtime code touched.

## Tests run

- None: no code changed.

## Decisions taken

- **legio is consumed as a library** (embedded host owning the pumps), not only
  as the `legio server` CLI.
- The new consumer is a **separate repository**.
- This turn is **design-only**.

## Known issues / open points

- **Name/domain to confirm**: the maintainer named the repo **`invoice`** while
  the analyzed domain is voice-notes. The design is being kept domain-neutral
  until this is confirmed (it changes the repo name, package name, pattern
  names and prompts).
- **Host-shell reuse**: `serve_node` cannot inject composite classes; the
  embedder replicates the host loop today. A domain-free legio improvement
  (a `composite_classes` parameter on `serve_node`, or a public `legio.host`
  helper) is a candidate future issue — not required for the design.
- Composite classes are supplied by the consumer (11 classes = 9 main + 2 text
  composites), until/unless option B (a node-local composite loader) lands in
  legio.

## Next steps

1. Confirm the repo name/domain (`invoice` vs voice-notes).
2. Write the consumer plan/contracts (once the name is fixed), then the first
   vertical slice (smallest main pattern end-to-end with a fake STT + `MockLLM`).
