Findings (recorded here; no artifacts added to legio — AGENTS.md rule 7 forbids
consumer domain content):

1. **What voice-notes is.** A monolithic FastAPI app with a bespoke engine over
   `beaver-db` + `argo-ai` + `castor-io`. Domain: upload a voice note → external
   STT transcription → a set of LLM text processors (summary, categories, key
   ideas, main goal, events, email draft, to-dos, entities, agenda,
   interventions, agreements, Q&A, article outline, context, conclusion,
   project plan) → structured JSON. 10 "main" patterns (`idea`, `blog_post_draft`,
   `reminder`, `email_simple_draft`, `to_do`, `meeting`, `interview`, `generic`,
   `project_roadmap`) are each `sequence: transcription → parallel: processors`.
   2 composite text processors (`draft_writing`, `executive_summary_flow`).
2. **The legacy engine details that legio already superseded**: a
   `FlowControlToken` carrying a mutable `blackboard`; `SequenceAgent` /
   `ParallelAgent` with per-class `state:parallel:<agent>` dicts + beaver locks
   for fan-out/fan-in; agent-level re-queue retries; a distributed LLM
   semaphore; `PatternLoader` compiling pydantic models from `output_schema`,
   promoting inline composites, and computing reachability; `castor` Manager
   tasks (`run_agent_crew_worker`, `start_voice_note_workflow`); `argo` LLM.
3. **Mapping already provided by legio**: token/messages, standing atomic
   tool/linguistic agents, the unified `CompositeAgent` (branches + gathering
   queue + per-`branch_id` slots, no per-class locks), Runtime/Registry/Manager
   lifecycle with pools, `lingo` structured LLM, Schema 1/3 load+compile,
   client tokens, federation, and the polling host.
4. **Gaps / semantic changes that make the legio version "different"**:
   - **Composite classes are injected programmatically only.** The CLI
     `legio server` calls `boot_node(loaded)` with no `composite_classes` and no
     node-local composite loader, so **any node with a composite cannot boot via
     the CLI**; the five examples' composites are exercised only by tests that
     define and inject a `GatherComposite`. A consumer with composites must
     embed legio in Python (or a new domain-free loader must be added).
   - **Payload is construction + re-keying, not blackboard accumulation.** Each
     step builds exactly `{output_as: value}` and the next reads under its
     `input_as`; the legacy "every processor sees the whole blackboard" (and the
     `find_and_promote_context` hack) do not exist. Parallel processors receive
     the transcription via the composite's re-keying; cross-step context must be
     carried explicitly or by nesting.
   - **No engine retries / no re-queue.** `policy.retries` must be `0` (a
     non-zero value refuses the tool); the legacy `max_retries` / `retry_delay_s`
     and tenacity HTTP retry must move inside the tool implementation.
   - **No distributed semaphore** (docs: future scope) — scale is pool size and
     federation.
   - **Application layer stays in the consumer**: audio upload/storage, user
     auth/quota, the admin token CRUD (stubbed in the legacy app), and the
     Streamlit client. legio owns only submit/status + client tokens + node
     security.
   - **Result shape**: the legacy flattens the blackboard, strips internal keys
     and honors `final_output_key`; legio returns the composite's
     `build_output_as` payload — the new output contract must be declared
     explicitly.
   - **No inline composites / no implicit composition**: every step is a named
     pattern with the mandatory symmetric `input`/`output` triples; the legacy
     main/audio/text hierarchy becomes `patterns/{tool,linguistic,composite}`
     with `main: true`.

# 2026-09-28 — Session 130 (turn 4): defect analysis — composite loading + retries

## Scope

Maintainer flagged two implementation defects as unacceptable and asked for an
analysis: (a) a node with composites does not boot via the CLI, although
composites must always be loadable; (b) retries were decided generally but the
implementation rejects them. This turn is **analysis only** (no code): confirm
both against the code and the approved contracts, name the root causes, and
propose the corrective slices.

## Work done (analysis, with evidence)

### Defect A — a composite node cannot boot via the documented CLI

- **Reproduced**: `uv run legio server --config examples/summarize/legio.yaml`
  fails at boot with
  `composite 'summarize' has no concrete composite class injected`.
  (It first needs a dummy `LEGIO_LLM_API_KEY` for the local LLM client — a
  separate, minor friction, see below.)
- **Root cause**: `BootedNode`/`boot_node` accept `composite_classes`, but
  **nothing in the CLI supplies them**: `server_command` → `serve_node` →
  `boot_node(loaded)` with no classes, and `server_command` exposes no option to
  provide them. There is **no node-local composite-class loading mechanism**
  (asymmetric with node-local tools, LEG-104). `_materialize_composite` raises
  `UnrecoverableError` when the class map lacks the pattern.
- **Design vs defect**: LEG-040 consciously specifies **no generic default
  build** (output construction is the pattern's model). That is not the defect.
  The defect is that **the consumer has no way to provide the concrete classes
  to a node booted by the CLI** — so the shipped, documented composite examples
  (`summarize`, `extract-and-summarize`, `distribute-summary`,
  `document_processing`) cannot run with the documented command; LEG-104 proved
  only `transform` (no composite). This contradicts the Consumer Guide §8
  ("your composite class ... is injected at boot") and the examples promise
  that each node is copy-and-run.
- **Fix direction (contract-first)**: node-local composite-class loading
  symmetric to LEG-104's node-local tools — a `composites.py` beside the node
  config whose concrete classes are discovered, loaded by file location, and
  injected by `boot_node`; plus a CLI override; plus a subprocess test that
  boots a composite example end-to-end.

### Defect B — `policy.retries` is rejected although the contract defines it

- **Approved contract LEG-013** (§Contract & design): "`policy.retries` = how
  many times the executing entity retries the **call**; `policy.timeout` = how
  long you may wait **per call**." Schema 3 and AGENT_LIFECYCLE §Schema 3 say
  the same (`retries: <call retries>`).
- **Implementation**: `ToolAgent._tool_policy` rejects any non-zero `retries`
  ("only retries=0 is supported (steps are never retried)"); the loader accepts
  `retries >= 0` but execution refuses `!= 0`. So the declared policy is a lie.
- **Root cause / conflation**: the Session 16 ruling ("no lease, no retry, no
  re-queue **in the dispatch**") is about the **dispatch step** never
  re-queueing a raised step; LEG-103 Slice 1 then over-applied it to the
  **tool call** ("retries stays 0"), contradicting LEG-013. A tool *call* retry
  (same step, bounded attempts, under the per-call timeout) is compatible with
  polling-only and with "a raised step is never re-queued".
- **Fix direction (contract-first)**: honor `policy.retries` as bounded
  tool-call retries; keep the dispatch re-queue forbidden; amend the LEG-103
  Slice 1 clause and its tests.

### Minor observation (not the maintainer's two)

- `default_lingo_factory` builds `lingo.LLM(api_key=None)` when
  `LEGIO_LLM_API_KEY` is unset, and the OpenAI client raises even for a local
  OpenAI-compatible endpoint (the examples' `localhost:11434/v1`). The
  documented linguistic examples therefore need a dummy key. Candidate small
  fix/decision, separate from A/B.

- None: analysis turn; no runtime code changed.
