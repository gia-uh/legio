# 2026-09-05 — Session 40 — LEG-070 cascade invalidation (R-7): the catalog is a dependency DAG over composite branches

## Scope

Per rule 12, the maintainer authorized implementing **LEG-070** (the R-7 first
issue) — approving the DRAFT spec (`docs/CONTRACTS/LEG-070-cascade-invalidation.md`).
Its contract: disabling one (possibly broken) pattern transitively disables every
pattern that depends on it; the catalog reflects the invalid/disabled set; invalid
patterns are removed from the served catalog; invalidation is visible (a pattern
referencing an invalid dependent is reported disabled), never masked; failures are
never silent (rule 9).

## Work done

**Runtime (`src/legio/`).**
- `patterns/schema1.py` (the catalog model — state lives where the contract says
  "catalog reflects"):
  - `Catalog` is now a **dependency DAG** over composite `branches` (reuse by
    reference; no cycles load, LEG-021). New observable state field `invalid:
    frozenset[str]` — the loaded `specs` stay read-only; invalidation never mutates
    them, so a disabled pattern keeps its spec record (the lifecycle `disable` is
    reversible).
  - `invalidate(name) -> frozenset[str]` — BFS transitive closure over
    `dependents` (composites whose any branch references the current node),
    records the closure in `invalid`, logs the chain, returns the **newly
    invalidated** set. **Idempotent** (re-invalidation is a no-op, per the approved
    resilience model) and **never silent**: an unknown pattern raises
    `UnrecoverableError`.
  - Served view: `served()` = loaded minus invalid; `is_served(name)`,
    `is_invalid(name)`; `dependents(name)` (direct).
- `patterns/loader.py` `resolve_branch`: a branch step referencing an **invalid**
  pattern is refused with `UnrecoverableError` ("branch references invalid pattern
  … not served") — the reported-denial enforcement where the engine consumes the
  catalog to build routes; `resolve_composite_branches` inherits it.
- `api.py` `_resolve_route`: a starting agent the catalog has invalidated is
  **not routed** — raises (`"agent not served by catalog … invalid/disabled"`)
  instead of silently falling back to a `((name, name),)` route.

**Tests (`tests/`) — contract-first (red → green).**

# 2026-09-05 — Session 60 (REVERTED) — Supervisor: REJECTED — re-introduced the instance-supervisor/central-scheduler the design forbids

## Scope

I proposed and committed a `NodeRuntime.supervise()` that polled **every**
materialized agent in a central loop until idle ("the node's single polling
loop"). The maintainer rejected it outright — correctly — as a re-introduction
of the **instance supervisor / central scheduler** that `AGENT_LIFECYCLE.md`
§0/§6.1/§4.4.7/§10.7 explicitly eliminate, and as coupling the boot/orchestrator
should not have. Commit `6b9a103` was reverted (`687070f`).

## What the approved design actually says (rule 12)

- **Runtime** = the only layer with initiative, the public face (lifecycle
  ops + submit/status interface). It **never executes agent work** and **does
  not touch the agents' running/run loop** — it brings agents up/down and
  fronts the submits (§0, §6.1).
- **Agent** = a standing actor that **polls its own class queue with its own
  loop**; "there is no central scheduler: instances (agents) poll their own
  queue" (§0, §1.2, §12.2). The agent's loop is a **callable** a TaskManager
  task runs; the node's **task executors drain the TM queues**, scheduling by
  the `next_run_at` **field** on the task record (§0, §6.1).
- **TaskManager** = the domain-free **executor of facts**: it runs the callable
  that is an agent's internal loop (create_instance = `submit(agent_loop, ...)`),
  pauses/resumes/cancels it. It is blind to the domain and to the DAG; it owns
  `next_run_at` scheduling on **task records** (`tm_scheduled` priority queue).
  It is **not** a business-task engine and **not** an agent dispatcher.
- **No instance supervisor** (§4.4.7/§10.7): "the TM is executor only; the
  Runtime decides; the agent's internal cycle is the callable's own — the agent
  is not a task, its identity lives in the catalog".

## Why `supervise()` was wrong (the violations I introduced)

- It is a **central scheduler polling every agent** — the exact "instance
  supervisor" the design removes ("no instance supervisor", "no central
  scheduler").
- **Coupling**: the boot/product now wakes and drives each agent's lifecycle
  loop; agents are supposed to be **self-polling** actors, and who runs their

# 2026-09-05 — Session 60c — Two physical queues per composite (inbox + gathering); gated polling ratified

## Scope

Maintainer-led design ratification (this turn) of how a **composite** consumes
its queues, plus the physical-queue split the current code violates. Corrects my
two misreadings this turn (first I said "one single queue dispatch-by-type",
then "two queues at the logical level is what blocks complexity"). The ruling,
verbatim intent: the composite has **TWO PHYSICAL queues** — its class inbox and
its gathering — to *avoid* the computational complexity and error risk of the
logical split (inspecting every message, dispatching by type, differentiated
processing, skipping the input contract for some message kinds). No code/spec
authored; model ratified and recorded for the runtime-triangle spec.

## The ratified model

**Two physical queues, partitioned by construction:**
- **Inbox** (`legio:queue:<class>`, §12.2) — carries ONLY `EXECUTION_REQUEST`
  (entry/invocations). The input contract applies here, uniformly.
- **Gathering** (`legio:gather:<agent_id>`, §12.3 "the composite has one
  gathering queue") — carries ONLY the composite's own branch returns
  (fan-in `EXECUTION_RESULT`). No input contract, structurally guaranteed.

The partition removes all per-message decisions: what comes out of the inbox is
a request (fan-out); what comes out of the gathering is a result (fan-in). The
**inlet IS the type distinction** — no `MessageType` dispatch, no conditional
contract application, no misrouting classes.

**Polling (maintainer-authored, ratified "así es, te pareció correcto? yes"):**
1. **Intake cycle — unconditional on the inbox.** If a request arrives, fan it
   out to its branches and **annotate a pending task** in the internal
   bookkeeping keyed by the flow's `task_id` (`state:<composite>`).
2. **Collection cycle — conditional on pending.** Poll the gathering ONLY when
   at least one task is pending (with none pending there is nothing legitimate
   to receive; polling would be a pointless cost). Collect each branch result
   into the task's slots (conserving `branch_id`); when ALL of that task's
   fan-in has arrived, mark the task **terminated-for-the-composite** (internal
   bookkeeping only), build the output, re-key, and route to the next queue per
   the continuation token's `end_of_level_queue`.
3. A message arriving on the gathering with no pending task is, by flow
   well-formedness, an anomaly → **visible error (rule 9)**, never silently
   processed. The gate turns well-formed flows into saved polls and malformed
   ones into loud symptoms.

**Principles preserved:** per-cycle fairness (one inbox + one gather item when
pending; no starvation either way); ordering between a request and a result is
irrelevant (bookkeeping keyed by `task_id`, disjoint); the composite touches
only its own inbox, its own gathering, its own `state:<composite>` and the next
queue the token names — never another agent's queue (rule 7/8, no coupling);
"terminated-for-the-composite" is private to the agent (invisible to TM and
Registry); atomic agents keep their single inbox (they have no fan-in).

## Audit note updated (rule 12)

The shipped `composite_agent.py` **collapses the gathering onto the inbox**
(`end_of_level_queue=self._agent_id`, comment "collapsed onto its own queue, by
message-type dispatch") and dispatches by `MessageType` in `_handle`
(`composite_agent.py:87-93`), with `AgentBase._verify_input_contract`
special-casing `EXECUTION_RESULT`. That is exactly the rejected pattern — a
single mixed queue resolved *logically*. It is now registered as a **divergence
to fix** in the runtime-triangle slice: the composite must own a second physical
queue `legio:gather:<agent_id>`, its fan-out stamps `end_of_level_queue` =
that gathering, and its runner uses the two-cycle intake/collection poll above.

## Decisions taken

- Composites have **two physical queues** (inbox of class + own gathering);
  atomics have one (their class inbox). The transport partition, not message
  inspection, distinguishes requests from results.
- The composite polling policy is the ratified two-cycle: intake unconditional,
  collection gated by pending; join = bookkeeping (`state:<composite>` keyed by
  `task_id`, slots per `branch_id`), never polling-blocking, never locked
  globally.
- The "gathering collapsed into the inbox + MessageType dispatch" shipped code
  is a divergence to fix under this slice (with `legio:gather:<agent_id>`
  naming and `_deliver` disambiguation between per-task result and per-composite
  gather targets).
