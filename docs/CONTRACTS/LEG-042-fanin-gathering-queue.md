# LEG-042 — Fan-in: gathering queue by (composite, task, branch) identity

- **Status:** DRAFT (rewritten to the unified `type: composite` model)
- **Rasante:** R-4
- **GitHub issue:** #25
- **Source:** `docs/PLAN.md` (LEG-042)
- **Depends on:** LEG-023, LEG-040, `docs/AGENT_LIFECYCLE.md` §12.3/§12.4

## Goal

The composite fan-in (per-composite **gathering queue**, bookkeeping
`state:<composite>`, AGENT_LIFECYCLE §12.4): join the return of every branch of
a task exactly once, in a slot-stable way (each branch has a fixed
`branch_id` from fan-out, even before it returns), and behave correctly — never
silently — when a branch is bugged or missing.

## Scope

- **In scope:** gathering structure, join slot stability, exactly-once join,
  visible failure when a branch never returns.
- **Out of scope:** agent-level behavior (composite runner on top, LEG-040);
  pools (LEG-080).

## Contract & design

- The payload travels **in the messages** (AGENT_LIFECYCLE §12.1);
  the gathering queue of the composite class is a **second physical queue**
  (`legio:queue:gather:<agent_id>`, distinct from the class inbox, §12.3) that
  holds the children's `ExecutionResultMessage` returns from which the composite
  **builds its payload** — there is **no** out-of-message accumulator and no
  central store. Results are partitioned **by queue**, never by message type.
- A result landing on the gathering with no pending fan-out (the composite's
  collection cycle is **gated by its pending bookkeeping**, §12.3/§12.4) is an
  **anomaly surfaced visibly** (AGENTS.md rule 9), never processed silently and
  never re-deposited.
- The composite's bookkeeping (`state:<composite>`, keyed per task) records
  the continuation and one slot per branch, each slot pre-created at fan-out and
  filled when that branch's result returns; the join completes when every slot
  of the task is filled.
- Dedupe per **(composite, task, branch slot)** — enforced by bookkeeping keyed
  directly on the constant `task_id` (the same across the whole fan-out, LEG-040)
  and by slot identity from the result's `branch_id` (autogenerated by the
  composite at fan-out): two branches — even two that are the very same
  class/sequence — are two distinct slots; no join by agent name.
- **Join→advance ordering (crash-safe).** The advance deposit happens before
  the join row is deleted (advance-then-delete): a crash that lands between the
  two leaves a stale join row rather than orphaning the parent route.

## Interface

- Gathering-queue composition API; step join resolution API.

## Acceptance criteria

From `docs/PLAN.md` (LEG-042), verbatim:
- Two branches of one composite task join exactly once each; a missing/bugged
  branch result is surfaced visibly, never silently; join slots are stable from
  fan-out (slot-stable even before a branch returns).
