# LEG-040 — Composite agent (unified runner: branches, fan-out, gather, build)

- **Status:** DRAFT (rewritten to the unified `type: composite` model, superseding
  the former SequenceAgent/ParallelAgent split)
- **Rasante:** R-4
- **GitHub issue:** #23
- **Source:** `docs/PLAN.md` (LEG-044)
- **Depends on:** LEG-023, LEG-031, LEG-011, `docs/AGENT_LIFECYCLE.md` §12.3/§12.4

## Goal

Implement the **composite agent** — the single agent class for `type: composite`
(AGENT_LIFECYCLE §4.10/§4.11). A composite has `branches` (a list of ordered
step sequences); a single branch is a sequence, multiple branches are a
parallel — both are **the same runner**, the same code path. The runner:
ramifies to its branches, gathers the fan-in on one **gathering queue**, and
builds its declared `output_as` from the branch results.

**Ordering is by chain deposit, never by locking.** No agent waits on another
and nothing is blocked: a step runs as soon as its item arrives in its queue.
The order is encoded in the token's `level_route`/`current_index`, not enforced
by any lock. This is the polling, decoupled philosophy (AGENTS.md rule 8).

## Scope

- **In scope:** composite fan-out (depositing each branch's own loader-resolved
  `level_route`), fan-in gathering (join per `(task_id, branch_id)`, exactly-once,
  slot-stable), building the composite's `output_as` from branch results, and
  advancing the composite's own level on fan-in completion. Re-keying at every
  hop (§12.1).
- **Out of scope:** pools (LEG-080), federation delegation.

## Contract & design

- There is **one** composite agent class (Schemas 1/4.11): `type: composite`
  with `branches`. No `SequenceAgent`, no `ParallelAgent`, no `kind:
  sequence|parallel`. A composite carries neither `tool` nor `prompt` — only
  `branches` and the mandatory entry/output contract triples (`input_as`/
  `input_type`/`input_schema`, `output_as`/`output_type`/`output_schema`).

- **Fan-out.** On receiving its request, the composite does **not** advance while
  its branches run. It fans out: for each branch it deposits that branch's
  **loader-resolved `level_route`** (its `(class, input_as)` steps) with
  `current_index = 0`, `end_of_level_queue` = the composite's **gathering queue**,
  `level + 1`, and a **fresh autogenerated `branch_id`** (uuid4, unique — no
  parent-derived naming — distinct from its own and from every other branch across
  all levels; constant along the branch's sequence, carried on the message). The
  composite re-keys its shared `input_as` under each branch's first step's
  resolved `input_as` (§12.1). A branch may be atomic (sequence of size 1),
  a multi-step sequence, or another composite (recursive inner ramification).

- **Fan-in.** Each branch, on branch close, deposits its
  `ExecutionResultMessage` to the gathering queue **conserving its `branch_id`**
  (failures conserve it too — an `error` result, rule 9). The composite
  accounts for fan-in **one result per `branch_id`**: its gathering bookkeeping
  is keyed by `(task_id, branch_id)` under a lock (`state:<composite>`). The
  join counts slots until all of the task's `branch_id`s are present.

- **Build.** On fan-in completion (all `branch_id`s accounted for), the
  composite **groups the branch results collision-free**: each branch's built
  payload `{output_as: value}` stays under its own autogenerated `branch_id`
  slot (uuid4 — distinct per branch of the task, so two leaves ending in agents
  with the **same** `output_as` never collide) and that grouped mapping is
  handed to the pattern's own **`build_output_as`** — the re-implementable seam
  on the agent (a concrete composite inherits `CompositeAgent` and composes the
  branch values into its own `output_as`, satisfying its declared
  `output_schema`). There is **no generic default build** in the engine (the
  engine cannot guess a shape that validates against an arbitrary declared
  `output_schema`), no `emit:` map and no "last child renamed" rule.

- **Resume.** After building, the composite decrements `level` (−1) and resumes
  its own level (`current_index + 1` → next step), with `end_of_level_queue` the
  one its creator supplied. The token leaving it is re-keyed exactly like any
  advance (§12.1): the composite's `output_as` is re-keyed under the next step's
  resolved `input_as`. There is no special composite→output remap.

- **Parent continuation.** At branch close the result returns via
  `end_of_level_queue` to the composite's gathering queue (LEG-051). Nested
  composites: an inner composite's branch-close surfaces first to its enclosing
  composite's gathering queue; a composite at `level == 1` in last position
  delivers the final result to the submit's final-result queue (LEG-053).

- **Composite as root.** Submit passes the composite's route as level 1 with
  `end_of_level_queue` = final-result queue; branches run at level 2; after
  fan-in the composite resumes its level-1 route with the final-result queue.

- **Payload construction (§12.1).** Each agent in the branch receives the
  incoming payload re-keyed under its `input_as`, applies its outcome, and
  builds its own output under its `output_as` via `legio.flow.build_payload`
  (construction, NOT accumulation). On advance, the base re-keys the produced
  value under the next step's `input_as`; the last step delivers its `output_as`
  payload to the gathering queue. The built dict is exactly what the next request
  carries as `payload`.

## Interface

- Composite agent class (unified runner) implementing fan-out → gather → build
  for the `type: composite` agent. Build is the re-implementable `build_output_as`
  seam (no generic default: the pattern composes the slot-grouped branch results
  into its declared `output_as`). A single class, a single `run()`, no
  SequenceAgent/ParallelAgent split.

## Acceptance criteria

From `docs/PLAN.md` (LEG-044), verbatim:
- A single composite runner handles both single-branch (sequence) and
  multi-branch (parallel) cases identically.
- Fan-out deposits each branch's own loader-resolved `level_route` (not a single
  class); a multi-step branch whose returned `level_route` expands to its own
  internal steps still slots under the parent-assigned `branch_id`.
- Fan-in joins exactly once per `(task_id, branch_id)`; a missing/bugged branch
  is surfaced visibly (never silent).
- Branch results are grouped by their autogenerated `branch_id` slot
  (collision-free even for same-`output_as` leaves) and handed to the pattern's
  `build_output_as`; the composite builds its declared `output_as` from them.
- Nested composite branches (multi-step, composite-in-branch) run correctly.
- Re-keying applies at every hop: fan-out (composite's `input_as` → branch's
  first step's `input_as`), advance within a branch (step N's `output_as` →
  step N+1's `input_as`), fan-in resume (composite's `output_as` → next step's
  `input_as`).
- Suite green; docs consistent with the unified model.

## Tests

- Contract tests (red first):
  - Single-branch composite (sequence case): advances through its branch steps,
    builds its `output_as` on fan-in, resumes its level.
  - Multi-branch composite (parallel case): fan-out to N branches, all complete,
    fan-in joins by `(task_id, branch_id)`, builds `output_as`.
  - Nested composite: composite-in-branch closes to its parent's gathering queue.
  - Two same-class branches get distinct `branch_id`s.
  - Fan-in completeness: all branches accounted for before build.
  - Error propagation: a branch failure yields a visible error result, composite
    accounts for it (conserving `branch_id`).

## Validation case

- `extract_and_summarize` (sequence) and `distribute_summary` (parallel) —
  both run end-to-end over REST (LEG-025/LEG-027).
